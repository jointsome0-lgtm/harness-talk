# What works on which system

As of 0.15.0, with what came after it marked "after 0.15.0": that is in the source and in no release yet. Where 0.14.0 differs, the page says so. A cell says whether the part is ported and what stands behind the claim. "Runner" is a test on a GitHub-hosted runner of that system, run on every pull request by `tests.yml` and on every wheel by `publish.yml`. "Live" is a dated check with real clients on a person's machine. A runner is not a person's machine: no real Codex, Claude Code or OpenCode has run on macOS or Windows.

"Desktop check" below is the [October 10 check of the published Windows 0.14.0 wheel][windows-desktop] on an existing Windows 10 Pro x64 installation, with no client. Commands were entered individually in `cmd.exe` and Windows PowerShell through ConPTY; Ctrl-C was terminal input, not a physical keyboard press. The record retains the initial pip failure and the environment retry, and the original download channel of the existing Python was not established. This check adds evidence only for the operations it names, and is not a live client check.

A part that is not ported answers `unsupported_on_this_platform` with exit code 2 and writes nothing of its own. `peer check` opens the mailbox before it answers, and opening a schema-1/2 mailbox migrates it, as any ordinary command does. `peer discover` gives the code as the `detail` of each source it cannot ask, and exits with 2 when it could ask none. A notice to a peer whose delivery is not ported is recorded as not submitted with that code, and the message stays saved.

One part of native delivery stays on Linux. `peer discover` finds a Codex session on macOS through an app server only, because macOS keeps no table of held locks to read: the source `codex_writer_locks` answers `unavailable` with `unsupported_on_this_platform`.

After 0.15.0 Windows has one route into Codex: `codex queue`, the command of the installed client, after a read of the client's `state_5.sqlite`. `peer add --harness codex` without `--socket`, `peer check` and a notice to such a peer work there. The rest of native delivery answers `unsupported_on_this_platform` on Windows: a Codex peer with `--socket`, the discovery of Codex sessions, taking a notice back after its message is acknowledged, `receive`, and Claude Code altogether. So `peer discover` finds no Codex session there, and the session id is given to `peer add` by hand. An acknowledgment is saved as on every system, and its `notification_cleanup` says `unsupported` with that code: the notice stays in the client's queue.

htalk does not run the `codex.cmd` that npm puts on the path, because a `.cmd` file cannot be given an argument with a line break, and a notice has several. It looks through the directories of `PATH` in their order. A `codex.exe` is started itself. Of a `codex.cmd` it reads the script the file names and starts `node.exe` with it, the one beside the file or else the first on the path, as the file itself would. A `codex.cmd` it cannot read so, or no `node.exe`, is `file_not_found`, and nothing is submitted. The command has twenty seconds and runs in a job, so what it started ends with it, by Ctrl-C too. [Adapters](adapters.md#codex-on-windows-through-its-installed-command) records what this was written from. It was checked on the runner against a fake client only, and a notice to a real Codex session on Windows is still to be seen.

A command that Claude Code runs on macOS is recognized as its session, as on Linux. htalk asks the system for the parent, the start and the executable of a process, and writes the start as `ps -o lstart=` prints it in UTC, which is how the packages of Claude Code for macOS record it. That was read from the packages, and a runner checks htalk's text against the system's own `ps`. No real Claude Code ran. A client nested in a session is seen there only when it is a program of its own, because macOS names a process that a script started after its interpreter.

The runners run 97 contract tests of 0.15.0 on each of the two systems. macOS skips none. Windows skips 39: the 37 of native delivery and the two that need a named pipe. After 0.15.0 there are 100. macOS skips the one that is about a system where a Codex notice is not taken back. Windows skips 32: 11 of Claude Code, 5 of the removal of a Codex notice, 4 of `receive`, 10 of the other parts of native delivery, and the two that need a named pipe. Every skip prints its reason. In 0.14.0 there were 87, of which macOS skipped 29 tests and subtests, all of native delivery, and Windows 31.

## The default mailbox

`--db PATH`, then `HTALK_DB`, then `$XDG_DATA_HOME/harness-talk/mail.sqlite3` when the variable is set and not empty, on every system. Then:

| System | Path |
| --- | --- |
| Linux | `~/.local/share/harness-talk/mail.sqlite3` |
| macOS | `~/Library/Application Support/harness-talk/mail.sqlite3` |
| Windows | `%LOCALAPPDATA%\harness-talk\mail.sqlite3` |

The [Windows desktop check of 0.14.0][windows-desktop] began with that directory absent. Registering the two pull peers created `mail.sqlite3` there. `icacls` showed inherited full-control entries for the current user, SYSTEM and Administrators on the directory and file, and no entries for Users, Authenticated Users or Everyone. These are the access lists of that profile, not a guarantee for a mailbox placed elsewhere.

The file is schema 3 on every system and holds nothing that one system writes and another does not. Sharing one file between two systems over a network drive was not checked, and htalk does not support it: locking and synchronization of a network filesystem cannot be assumed reliable. The file is not encrypted, see [reference](reference.md).

## Limits to know

- macOS: SQLite syncs with the ordinary call of the system, which does not make the drive write its cache. `PRAGMA fullfsync` is not switched on, so a message saved a moment before a power loss can be missing afterwards. A crash of the program or of the system without a power loss loses nothing.
- Windows: the default mailbox is private because the profile directory is. htalk sets no access list. A `--db` somewhere else is as private as its directory.
- Windows: Ctrl-C and Ctrl-Break end a command with exit 130. The MCP server sends Ctrl-Break to a cancelled tool call that still runs and ends what is left two seconds later; in 0.14.0 it ended the call at once, with no request to stop. Ctrl-Break reaches a call that shares the server's console. Where it cannot be sent at all, as when the server has no console, the call is ended at once; a call that does not hear it is ended after the two seconds. The server ends its tool calls when it is killed itself.
- Windows: the [desktop check of 0.14.0][windows-desktop] observed Ctrl-C exit 130 for `send --wait` and `watch` in `cmd.exe`, and `$LASTEXITCODE` 130 for `send --wait` in Windows PowerShell 5.1. The `cmd.exe` code page was 866, while PowerShell's `[Console]::OutputEncoding.WebName` was already `utf-8`; both Cyrillic comparisons were `True`. The record does not establish how PowerShell reads the output under a different encoding. If it misreads UTF-8 output, set `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` before capturing it.
- Windows: a workspace is saved as `C:\dir`. A path longer than 260 characters is not supported as a workspace.
- WSL is Linux and is not what this page means by Windows.
