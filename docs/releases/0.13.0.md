# htalk 0.13.0

This version changes names and texts, once. Error codes are fixed words where they were Python class names, a command that worked answers with less, and the help and the MCP tool say the same thing. No command, option or exit code was renamed, and the mailbox is untouched.

A program that passes arguments and reads `state`, `id`, `submission` and `reply` needs no change. One that compares an error code, reads `recovery` from a result that succeeded, or reads the text of the help or of a parser error should check the lists below.

## Upgrade and recovery

Mailbox schema remains 3. Existing schema-3 mailboxes need no migration, and no saved row is rewritten: a `notification_detail` saved by 0.12 keeps the name it holds. 0.12.0 and 0.13.0 can read and write the same mailbox. The first ordinary command opening a schema-1/2 mailbox still creates and verifies a private SQLite backup in `MAILBOX_PATH.backups`, then migrates it to schema 3 in one transaction. Htalk never restores an old backup automatically.

Stop writers and receivers before replacing their CLI and matching adapter files. Update every installation that shares the mailbox, and take the adapter files from the 0.13.0 source archive. For a uv-installed CLI with a matching published Linux wheel:

```sh
uv tool install --force --no-build harness-talk==0.13.0
htalk --version
htalk peer list
```

Without uv, run `python -m pip install --upgrade harness-talk==0.13.0` in the intended environment. Check a read-only command, passive receiver status and existing receipts before resuming work. Do not reset state or resend an uncertain message to recover. The [0.11.0 adapter, recovery and Linux/pidfd requirements](0.11.0.md#upgrade) still apply.

Rollback is replacing the executable and its adapter files with 0.12.0, with affected processes stopped. Schema 3 is the same in both. A detail code saved by 0.13 stays in its row and 0.12 prints it as saved. Reverting the executable does not reverse native actions or reconcile uncertain work.

## Error codes

Where 0.12 printed a Python class name, 0.13 prints a fixed code. [The reference](../reference.md#error-codes) has one row for each code, with what it means and what to do. A mailbox command still answers a file or database failure of its own mailbox in the system's words, such as `database is locked`, as before.

These values appear as `error`, as `notification_detail`, as a cleanup `detail`, and as the `detail` or `error` of a discovery source.

| 0.12 | 0.13 |
| --- | --- |
| `FileNotFoundError` | `file_not_found` |
| `PermissionError` | `permission_denied` |
| `ConnectionRefusedError` | `connection_refused` |
| `ConnectionResetError`, `ConnectionAbortedError`, `BrokenPipeError` | `connection_closed` |
| `TimeoutError`, `BlockingIOError` | `timed_out` |
| `OSError`, `IsADirectoryError`, `NotADirectoryError`, `FileExistsError`, `InterruptedError`, `ChildProcessError`, `ProcessLookupError` | `os_error` |
| `KeyboardInterrupt` | `interrupted` |
| `CalledProcessError` | `command_failed` |
| `TimeoutExpired` | `command_timed_out` |
| `OperationalError` from a client's database | `client_database_unavailable` |
| `DatabaseError` | `client_database_corrupt` |
| `OperationalError` when htalk could not read its own notification state | `notification_state_unavailable` |
| `JSONDecodeError` | `invalid_json` |
| `UnicodeDecodeError` | `invalid_utf8` |
| `KeyError`, `TypeError`, `AttributeError`, `ValueError` for a client's record of another shape | `invalid_client_data` |
| the same four for the answer of `claude agents --json` | `invalid_claude_agents_response` |
| `TOMLDecodeError`, `TypeError`, `UnicodeDecodeError` for the Codex config | `invalid_codex_config` |
| `ValueError`, `UnicodeDecodeError` for the lock table | `invalid_lock_table` |
| `ValueError` for a Codex receipt without a queue id | `codex_cli_invalid_queue_id` |
| `JSONDecodeError`, `AttributeError`, `KeyError`, `UnicodeDecodeError` for a Codex RPC answer | `codex_rpc_invalid_response` |
| `TimeoutError` in a Codex RPC call | `codex_rpc_timeout` |
| `ValueError`, `OSError` for a closed Codex RPC pipe | `codex_rpc_closed` |
| `opencode_BadStatusLine`, `opencode_HTTPException`, `opencode_IncompleteRead`, `opencode_LineTooLong`, `opencode_UnknownProtocol` | `opencode_invalid_response` |
| `opencode_RemoteDisconnected`, `opencode_ConnectionResetError`, `opencode_BrokenPipeError` | `opencode_connection_closed` |
| `opencode_TimeoutError` | `opencode_timed_out` |
| `opencode_SSLError` | `opencode_tls_failed` |
| `opencode_KeyboardInterrupt` | `opencode_interrupted` |
| `opencode_InvalidURL`, `UnicodeEncodeError` for the address | `invalid_opencode_url` |
| `UnicodeEncodeError` for the credentials | `invalid_opencode_credentials` |
| `opencode_<other class>` in discovery | `opencode_<code from the rows above>`; a code htalk already had passes without the prefix |
| `opencode_saved_OperationalError` | `opencode_saved_database_unavailable` |
| `opencode_saved_DatabaseError` | `opencode_saved_database_corrupt` |
| `Port could not be cast to integer value`, `Port out of range 0-65535` from `peer add --url` | `invalid_opencode_url` |
| `badly formed hexadecimal UUID string` from `send --id`, `show`, `reply`, `ack` | `invalid_uuid` |
| `invalid_arguments` from `peer add` without `--session` or `--workspace` | a usage error on stderr, see below |

A system failure is named by its kind, not by its errno, so the rarer errno names are `os_error`. A `claude agents --json` answer that is a JSON object or a string is `invalid_claude_agents_response`; it used to count as an empty list.

## The catalogue and `htalk mcp`

| Where | 0.12 | 0.13 |
| --- | --- | --- |
| A failed `htalk catalog` command that answers on stdout | `{"state":"error","error":CODE}` | the same with `next_action`: "Correct what the error code names and run the command again. htalk catalog --help lists the commands." |
| A `catalog` command that cannot read or write a file | the sentence of the operating system, such as `No such file or directory (os error 2)` | `file_not_found`, `permission_denied` and the other codes of the system |
| A `catalog` command that cannot read the mailbox | the sentence SQLite gives | `database_unavailable` or `database_corrupt` |
| `htalk mcp --catalog FILE`, `htalk mcp --connect`, `htalk catalog connect`, on stderr | `htalk mcp: No such file or directory (os error 2)` | `htalk mcp: file_not_found` |
| `htalk mcp` without `--as` and without `HTALK_PEER`, on stderr | `… or HTALK_PEER: invalid_peer_name` | `… or HTALK_PEER: peer_required_use_as_or_HTALK_PEER` |
| `catalog discover` and `catalog connect` on `lan` without `--interface` | a panic, exit 101, once the trust file was read | a usage error, exit 2 |

`catalog connect` and `catalog serve` still answer a failed start on stderr as `htalk catalog: CODE`, because their stdout is an MCP stream.

## Results of commands that worked

`next_action` and `recovery` are in a message only when something is not settled: `submission` is `submission_unknown`; or it is `not_submitted` and `notification_detail` names a failure; or the reader is the recipient and `notification_cleanup.status` is `pending`, `unknown` or `unavailable`. Then they are word for word what 0.12 printed. An error and an interrupted result keep both.

| Where | 0.12 | 0.13 |
| --- | --- | --- |
| A message whose notice was submitted or never due, from any command | `next_action`, `recovery{show, wait, show_reply, ack_after_reading}` | neither key. Use the message's `id`: `htalk show ID`, `htalk wait ID`, `htalk ack ID`. |
| Every message and every nested `reply` | `notification_started_at`, `notification_finished_at`, `wait_returned_at` | not in a result; still in the mailbox file |
| `inbox` or `sent` with more behind the page, also through the catalogue | `recovery.next_page`, and a sentence in `next_action` | `next_page` |
| `inbox` | `next_action`: "Read and ack messages explicitly. Unanswered questions remain until replied to." | no `next_action` |
| `peer discover` | `next_action`: "Choose an exact session address and register it with peer add. Discovery does not register or notify anyone." | no top-level `next_action`; a source that is unavailable keeps its own |

On one exchange between two pull peers a `send` answer went from 867 to 347 bytes and an `inbox` with one message from 1,034 to 369.

The help of all pages is 21,826 characters, 20 fewer than in 0.12. The MCP tool description is 1,102 characters, 227 more.

## OpenCode

The adapter speaks HTTP through `ureq` instead of code of its own.

| Where | 0.12 | 0.13 |
| --- | --- | --- |
| An answer cut off inside its body | `opencode_invalid_response` | `opencode_connection_closed` |
| An HTTPS handshake that the other side ends by hanging up | `opencode_unreachable` | `opencode_connection_closed`; the notice is `not_submitted` as before |
| A status line with two spaces and no reason phrase | accepted | `opencode_invalid_response` |
| `https://localhost` when the name resolves to a loopback address and to another one | the loopback address is used | `opencode_unreachable`; plain HTTP uses the loopback address as before |
| A 4xx answer whose chunked body lacks its last blank line | `submission_unknown` | `not_submitted` with `opencode_http_400` |
| A connection that breaks before any of the prompt was handed over | `submission_unknown` | `not_submitted` |
| Request headers and the JSON of the prompt | capitalized names; spaces after `:` and `,`, text outside ASCII escaped | lower-case names; compact UTF-8. The parsed value is the same. |

Frames to the Claude socket and to the Codex RPC are compact UTF-8 JSON too.

## Interrupts and the default path

| Where | 0.12 | 0.13 |
| --- | --- | --- |
| Ctrl-C during `ack`, while the Codex client removes the queued notice | answered about 11 seconds later | answered when the client's process is gone, at once or after 1 second |
| Ctrl-C during a `send` that holds its turn and waits for another writer | answered when the lock wait ends, up to 5 seconds later | answered at once, with nothing saved |
| A contended `send`, two times in three | probed for the other writer for up to 100 ms, and an interrupt in that window stopped the send before it was saved | no probe; the same sequence saves the message and answers `interrupted` with its id |
| `XDG_DATA_HOME=""` with no `--db` and no `HTALK_DB` | the mailbox is `harness-talk/mail.sqlite3` under the current directory | `~/.local/share/harness-talk/mail.sqlite3`, as with the variable unset |

The answers are the same in each case: exit 130, `state: interrupted`, and whether the message was saved.

## Where the agent view shows it

`tests/agent_view/` holds what an agent reads. Its files changed between 0.12.0 and this release as follows.

- `errors.txt`: the two lists of 0.12, error codes and detail codes, are one, and it holds the codes of the tables above where 0.12 said that a detail may be a class name. Four entries left it: `invalid_arguments` and `badly formed hexadecimal UUID string`, as the table says, and `command_required` and `peer_command_required`, which no input could produce because the parser already required a command. Five entries are in the list and in no table: `catalog_ssh_port_mismatch`, `opencode_invalid_saved_metadata`, `opencode_invalid_session_records`, `opencode_saved_metadata_missing` and `opencode_saved_session_limit_reached`. 0.12 had them; the tool that writes the list now reads the files they are in.
- `results.txt`: the keys of "Results of commands that worked", and two discovery details that are `file_not_found`.
- `help.txt` and `mcp.txt`: the section on the help.
- `texts.txt` lists source texts that no captured answer shows. It lost "A mailbox command is required.", the two port sentences and five lines of the HTTP request the adapter used to write; it gained three sentences of advice for a message that is not settled, "The command was interrupted. Run it again." for the catalogue, and the name "mcp, receive or catalog" of a refusal. These lines need no note of their own.
- `size.txt` is the count of the others.
- `notification.txt` has no change: the notice an agent receives is word for word the same.

## Code, tests and dependencies

- Production code: `src/` is 371,787 bytes in 10,259 lines. In 0.12.0 it was 398,404 bytes in 10,601 lines and held 29 of the Rust tests; it holds none now. The core that every command runs through is 41.5k tokens by `scripts/core_tokens.py`, and 74.7k with the adapters.
- Tests: 253, of them 192 in Python that run the installed command, 53 in Rust and 8 in Node. 0.12.0 had 96 Rust tests. `tests/agent_view/` is new: it holds every text an agent reads, and a test fails when one changes without the file.
- Dependencies: no direct dependency was added or removed. `clap` is used with its `derive` feature, which adds `clap_derive` and `heck` to the lock file. `ureq` is no longer pinned to one version and is used without its `json` feature. Ten packages left the lock file: `cookie`, `cookie_store`, `deranged`, `document-features`, `litrs`, `num-conv`, `powerfmt`, `time`, `time-core` and `time-macros`. It lists 205 where it listed 213.
- The build has one feature, `catalog`, on by default. `cargo install harness-talk --no-default-features` builds the mailbox without the profile catalogue.

## Source validation and limits

Each change was compared with the executable before it: 5,520 command lines, 7,898 with fake native clients, 66 commands on a saved mailbox, 57 MCP runs and 32 cases of locks, signals and paths. Every answer that differed was one a list above names. The executables of 0.12.0 and 0.13.0 wrote to one mailbox in turn and each read what the other saved. 253 tests pass: 192 through the installed command, 53 in Rust and 8 in Node.

These source checks do not show a notice arriving in a live client. The live checks of [releasing](../releasing.md) run on the published artifacts and are recorded in a dated check.
