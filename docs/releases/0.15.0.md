# htalk 0.15.0

This version brings notices into Codex and Claude Code to macOS, with their discovery, `htalk receive` and the recognition of the Claude Code session that runs a command. On every system the wait of a queued send is five seconds by the clock, and a Claude Code session started with `CLAUDE_CONFIG_DIR` is found. On Windows two limits of 0.14.0 are gone: an idle `watch` ends when its reader has gone, and a cancelled tool call of `htalk mcp` is asked to stop before it is ended.

What is new on macOS was checked on GitHub's hosted runners against the fake clients of the test suite, which answer as the published code of the two clients reads. No real Codex or Claude Code has run on a Mac, and no notice has reached a real session there. The first exchange on a Mac is a check that nobody has made yet. [What works on which system](../platforms.md) says what stands behind each line.

## Upgrade and recovery

Mailbox schema remains 3. A 0.14.0 mailbox needs no migration on any system, and no saved row is rewritten. 0.14.0 and 0.15.0 can read and write the same mailbox. The first ordinary command opening a schema-1/2 mailbox still creates and verifies a private SQLite backup in `MAILBOX_PATH.backups`, then migrates it to schema 3 in one transaction. Htalk never restores an old backup automatically.

Stop writers and receivers before replacing their CLI. Update every installation that shares the mailbox. The adapter files under `integrations/` are those of 0.14.0, unchanged. For a uv-installed CLI with a matching published wheel:

```sh
uv tool install --force --no-build harness-talk==0.15.0
htalk --version
htalk peer list
```

Without uv, run `python -m pip install --upgrade harness-talk==0.15.0` in the intended environment. Check a read-only command, passive receiver status and existing receipts before resuming work. Do not reset state or resend an uncertain message to recover. The [0.11.0 adapter, recovery and Linux/pidfd requirements](0.11.0.md#upgrade) still apply on Linux.

Rollback is replacing the executable with 0.14.0, with affected processes stopped. Schema 3 is the same in both. On macOS a Codex or Claude Code peer that was added with 0.15.0 stays in the mailbox. 0.14.0 saves a message to it and records its notice as `not_submitted` with `unsupported_on_this_platform`.

## Notices into Codex and Claude Code on macOS

| Command | Linux | macOS | Windows |
| --- | --- | --- | --- |
| `peer add`, `peer check`, `peer discover` for Codex or Claude Code | works | works since 0.15.0 | `unsupported_on_this_platform` |
| A notice to a Codex or Claude Code peer | submitted | submitted since 0.15.0 | `not_submitted` with the code; the message is saved |
| `receive` | works | works since 0.15.0 | the code, on stderr |
| `catalog` | works | the code | the code |
| `mcp`, `mcp --connect` and everything else, OpenCode peers among it | works | works | works |

A command that Claude Code runs on macOS without `--as` or `HTALK_PEER` acts as the peer of its session, as on Linux. htalk asks the system for the parent, the start and the executable of a process and starts no `ps`.

The port was written from what the two clients publish, and nothing of theirs was run on a Mac: Codex from its source at commit `99aa053` of 2026-10-08, Claude Code from the text inside its npm packages `2.1.295`. [Adapters](../adapters.md#codex-and-claude-code-on-macos-and-windows) records each line that was read, what a runner showed of the system, and what is not known without a live client. The runners exercise the port against fake clients that answer as those lines say: `test_cli_compat` and `test_receive` through the command, and the Rust tests of the transports and of discovery. Another version of a client can differ.

Three things differ from Linux:

- `peer discover` asks one source fewer for Codex. macOS keeps no table of held file locks that a program can read, so the source `codex_writer_locks` answers `unavailable` with `unsupported_on_this_platform`, and a Codex session is found through an app server only.
- A client nested in a Claude Code session is told apart from the session only when it is a program of its own. macOS names a process that a script started after its interpreter, so a nested client that is a script acts as the session's peer when it names none.
- The path of Codex's control socket must fit in 103 bytes, where Linux has 107. Under `~/.codex` it does. A longer one fails with `os_error`.

## On every system

A `send` or `reply` that found the mailbox busy and queued for its turn waited a count of short pauses in 0.14.0. It waits five seconds by the clock now, as every other writer has since 0.14.0. Seconds until `database is locked`, with the mailbox held by another writer:

| System | 0.14.0 | 0.15.0 |
| --- | --- | --- |
| Linux, one machine | 5.35 | 5.00 |
| Windows runner | 7.85 | 5.02 |
| macOS runner | not ended after 30, the limit of the test | 5.03 |

Claude Code keeps its files under `$CLAUDE_CONFIG_DIR` when that variable is set. 0.14.0 read `~/.claude/sessions` only: for a session started with the variable a notice was not submitted, `peer check` and `peer discover` did not find it, and a command it ran without `--as` was not recognized. 0.15.0 reads `$CLAUDE_CONFIG_DIR/sessions` when the variable is set and not empty in htalk's own environment. Without the variable every result is as before. The variable is the command's own: a command started without it does not find a session that was started with it. On Linux the place was tried with a signed-out Claude Code `2.1.295`; a notice to a signed-in session started with the variable was not tried.

## On Windows

- `watch` ends within about a second of its reader going, as on the other systems. In 0.14.0 an idle watcher stayed until a message arrived and its line could not be written. A pipe that refuses the question about its state is noticed at the next line, as before.
- The MCP server sends Ctrl-Break to a cancelled tool call that still runs and ends what is left two seconds later. In 0.14.0 it ended the call at once. Ctrl-Break reaches a call that shares the server's console. Where it cannot be sent at all, as when the server has no console, the call is ended at once.
- The MCP server is in a job of its own, so what its tool calls started ends when the server ends or is killed. A process that an `mcp --connect` connector starts in its first moment can still be outside the job of the call; it ends with the server at the latest, where in 0.14.0 it could outlive both.

## Limits

- macOS: notices into Codex and Claude Code, their discovery, `receive` and the recognition of a session rest on runners and fake clients. No real client ran.
- macOS: `PRAGMA fullfsync` is off, so a message saved a moment before a power loss can be missing afterwards.
- Windows: no notices into Codex and Claude Code and no `receive`.
- Windows: the default mailbox is as private as the profile directory; htalk sets no access list.
- macOS and Windows: the catalogue of profiles is not ported. OpenCode was checked against the test server of the suite, not against a real OpenCode. Of the session receivers of `integrations/` the JavaScript ones of Pi and Cline run on the runners with modeled SDK calls, and nothing backs the others there.

## Code, tests and dependencies

- Production code: `src/` is 11,053 lines; in 0.14.0 it was 10,848. `src/os/`, which holds everything that differs between systems, is 1,566 of them. The core that every command runs through is 43.6k tokens by `scripts/core_tokens.py`, and 77.1k with the adapters; in 0.14.0 it was 43.3k and 76.5k.
- Tests: 269, of them 201 in Python that run the installed command, 60 in Rust and 8 in Node. On Linux 56 of the Rust tests run, on macOS 47, on Windows 17; in 0.14.0 it was 55, 18 and 16. Of the Python tests 97 are the contract that runs on macOS and Windows. macOS skips none of them, where 0.14.0 skipped 29 of 87. Windows skips 39, each with its reason: the 37 of native delivery and the two that need a named pipe in the file tree.
- Dependencies: the lock file lists 205 packages, as in 0.14.0. `windows-sys` is asked for one more of its features, on Windows only.
- Rust 1.88 is still the lowest supported version.
- Wheels: Linux x86-64 and ARM64, macOS ARM64 and x86-64, Windows x64, as in 0.14.0. The contract tests run against each macOS and Windows wheel on a runner of its own system and architecture.

## Source validation and limits

`tests.yml` runs on Linux, macOS and Windows on every pull request. On Linux every check of 0.14.0 passes, and `tests/agent_view/` is the same as in 0.14.0.

These checks do not show a notice arriving in a live client. The native check of this release runs on the published artifacts on Linux, by the procedure of [releasing](../releasing.md), and is recorded when it is done. It does not cover macOS or Windows.
