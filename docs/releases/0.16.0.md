# htalk 0.16.0

This version brings one route of native delivery to Windows: a notice into Codex through the command that npm installs, `codex queue`. On Windows `peer add --harness codex` without `--socket`, `peer check` and a notice to such a peer work now. The rest of native delivery there still answers `unsupported_on_this_platform`. The README, which is also the project page on PyPI, opens with the install command and one exchange, and its links work on PyPI. On Linux and macOS nothing changed but the version.

What is new on Windows was checked on GitHub's hosted Windows runner against a fake client installed as npm installs the real one. No real Codex has run on Windows, and no notice has reached a real session there. [#147](https://github.com/jointsome0-lgtm/harness-talk/issues/147) is that check, with a real Codex CLI on a Windows desktop. [What works on which system](../platforms.md) says what stands behind each line.

## Upgrade and recovery

Mailbox schema remains 3. A 0.15.0 mailbox needs no migration on any system, and no saved row is rewritten. 0.15.0 and 0.16.0 can read and write the same mailbox. The first ordinary command opening a schema-1/2 mailbox still creates and verifies a private SQLite backup in `MAILBOX_PATH.backups`, then migrates it to schema 3 in one transaction. Htalk never restores an old backup automatically.

Stop writers and receivers before replacing their CLI. Update every installation that shares the mailbox. The adapter files under `integrations/` are those of 0.15.0; only one link in `integrations/README.md` changed. For a uv-installed CLI with a matching published wheel:

```sh
uv tool install --force --no-build harness-talk==0.16.0
htalk --version
htalk peer list
```

Without uv, run `python -m pip install --upgrade harness-talk==0.16.0` in the intended environment. Check a read-only command, passive receiver status and existing receipts before resuming work. Do not reset state or resend an uncertain message to recover. The [0.11.0 adapter, recovery and Linux/pidfd requirements](0.11.0.md#upgrade) still apply on Linux.

Rollback is replacing the executable with 0.15.0, with affected processes stopped. Schema 3 is the same in both. On Windows a Codex peer that was added with 0.16.0 stays in the mailbox. 0.15.0 saves a message to it and records its notice as `not_submitted` with `unsupported_on_this_platform`.

## A notice into Codex on Windows

| Command on Windows | 0.15.0 | 0.16.0 |
| --- | --- | --- |
| `peer add NAME --harness codex --session UUID --workspace DIR` | `unsupported_on_this_platform` | saves the peer |
| The same with `--socket` | the code | the code |
| `peer check` for such a peer | the code | finds the session in Codex's `state_5.sqlite` |
| A notice to such a peer | `not_submitted` with the code; the message is saved | submitted through `codex queue`, with `codex_cli_queued` and the queue id |
| `peer discover --harness codex` | the code for each source | the code for each source; the session id is given to `peer add` by hand |
| `ack` of a message whose notice was submitted | no such notice | saved; `notification_cleanup` is `unsupported` with the code, and the notice stays in the client's queue |
| `receive`, and Claude Code altogether | the code | the code |

htalk does not run the `codex.cmd` that npm puts on the path, because a `.cmd` file cannot be given an argument with a line break, and a notice has several. It looks through the directories of `PATH` in their order. A `codex.exe` is started itself. Of a `codex.cmd` it reads the script the file names and starts `node.exe` with it, the one beside the file or else the first on the path, as the file itself would. A `codex.cmd` it cannot read so, or no `node.exe`, is `file_not_found`, and nothing is submitted. A `.ps1` or `.bat` wrapper of another installer is not read.

The command has twenty seconds and runs in a job, so what it started ends with it at the limit or at Ctrl-C. At the limit the notice is saved as `submission_unknown` with `command_timed_out`, and it is not sent again.

The route was written from the npm package `@openai/codex` 0.162.1, read on 2026-10-10 UTC and not run. [Adapters](../adapters.md#codex-on-windows-through-its-installed-command) records what was read. The runner exercises it through the command in `test_cli_compat`, against a `.cmd` written as npm's cmd-shim writes it and a script in the place of `bin/codex.js` that runs the fake client. The notice arrives with its line breaks and with the quotes of a mailbox path that has them. A command that outlives its limit is ended with what it started. Another version of the client can differ.

## Limits

- Windows: the route into Codex rests on a runner and a fake client. No real Codex ran on Windows.
- Windows: Codex's control socket, the discovery of its sessions, taking a notice back after its message is acknowledged, `receive`, and Claude Code altogether answer `unsupported_on_this_platform`.
- Windows: in the moment between the start of `codex queue` and its entry into the job, a process it starts can be outside the job. It then ends with htalk at the latest, not at the limit.
- Windows: the default mailbox is as private as the profile directory; htalk sets no access list.
- macOS: as in 0.15.0, notices into Codex and Claude Code, their discovery, `receive` and the recognition of a session rest on runners and fake clients. No real client ran.
- macOS: `PRAGMA fullfsync` is off, so a message saved a moment before a power loss can be missing afterwards.
- macOS and Windows: the catalogue of profiles is not ported. OpenCode was checked against the test server of the suite, not against a real OpenCode. Of the session receivers of `integrations/` the JavaScript ones of Pi and Cline run on the runners with modeled SDK calls, and nothing backs the others there.

## Code, tests and dependencies

- Production code: `src/` is 11,242 lines; in 0.15.0 it was 11,053. `src/os/`, which holds everything that differs between systems, is 1,714 of them; in 0.15.0 it was 1,566. The core that every command runs through is 43.7k tokens by `scripts/core_tokens.py`, and 77.6k with the adapters; in 0.15.0 it was 43.6k and 77.1k.
- Tests: 272, of them 204 in Python that run the installed command, 60 in Rust and 8 in Node. On Linux 56 of the Rust tests run, on macOS 47, on Windows 17, as in 0.15.0. Of the Python tests 100 are the contract that runs on macOS and Windows; in 0.15.0 there were 97. macOS skips one: the test of a system where a Codex notice is not taken back. Windows skips 32, where 0.15.0 skipped 39, each with its reason: 11 of Claude Code, 5 of the removal of a Codex notice, 4 of `receive`, 10 of the other parts of native delivery, and the two that need a named pipe in the file tree.
- Dependencies: the lock file lists 205 packages, as in 0.15.0, and `Cargo.toml` asks for no new feature of any of them.
- Rust 1.88 is still the lowest supported version.
- Wheels: Linux x86-64 and ARM64, macOS ARM64 and x86-64, Windows x64, as in 0.15.0.

## Source validation and limits

`tests.yml` runs on Linux, macOS and Windows on every pull request. On Linux every check of 0.15.0 passes, and `tests/agent_view/` is the same as in 0.15.0.

These checks do not show a notice arriving in a live client. The native check of this release runs on the published artifacts on Linux, by the procedure of [releasing](../releasing.md), and is recorded when it is done. It does not cover macOS or Windows.
