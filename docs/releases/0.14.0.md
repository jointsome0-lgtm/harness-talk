# htalk 0.14.0

This version installs and keeps a mailbox on macOS and Windows. On Linux nothing changes but one new error code in the table of codes, and how the wait for a busy mailbox is timed.

On macOS and Windows 0.14.0 has installation from a wheel, the mailbox, pull peers, the MCP tool and OpenCode delivery. Native notices into Codex and Claude Code, `htalk receive` and the catalogue of profiles are Linux only. All of it was checked on GitHub's hosted runners. No real client has run on macOS or Windows, and no person has used it there. [What works on which system](../platforms.md) says what stands behind each line.

## Upgrade and recovery

Mailbox schema remains 3. A 0.13.0 mailbox on Linux needs no migration, and no saved row is rewritten. 0.13.0 and 0.14.0 can read and write the same mailbox. The first ordinary command opening a schema-1/2 mailbox still creates and verifies a private SQLite backup in `MAILBOX_PATH.backups`, then migrates it to schema 3 in one transaction. Htalk never restores an old backup automatically.

Stop writers and receivers before replacing their CLI and matching adapter files. Update every installation that shares the mailbox, and take the adapter files from the 0.14.0 source archive. For a uv-installed CLI with a matching published wheel:

```sh
uv tool install --force --no-build harness-talk==0.14.0
htalk --version
htalk peer list
```

Without uv, run `python -m pip install --upgrade harness-talk==0.14.0` in the intended environment. Check a read-only command, passive receiver status and existing receipts before resuming work. Do not reset state or resend an uncertain message to recover. The [0.11.0 adapter, recovery and Linux/pidfd requirements](0.11.0.md#upgrade) still apply on Linux.

Rollback is replacing the executable and its adapter files with 0.13.0, with affected processes stopped. Schema 3 is the same in both. On macOS and Windows there is no earlier version to return to.

## The new code

`unsupported_on_this_platform`, exit code 2: this part of htalk is not ported to the system it runs on. Nothing is written. A message to a peer whose delivery is not ported is saved, and its notice is recorded as `not_submitted` with this code, as with any notice that fails.

| Command | Linux | macOS | Windows |
| --- | --- | --- | --- |
| `peer add`, `peer check`, `peer discover` for Codex or Claude Code | works | the code | the code |
| `receive` | works | the code, on stderr | the code, on stderr |
| `catalog` | works | the code | the code |
| `mcp`, `mcp --connect` | works | works | works |
| everything else, OpenCode peers among it | works | works | works |

## Default paths

`--db`, `HTALK_DB` and `$XDG_DATA_HOME/harness-talk/mail.sqlite3` come first on every system, as before. Without them:

| System | Mailbox |
| --- | --- |
| Linux | `~/.local/share/harness-talk/mail.sqlite3`, as in 0.13.0 |
| macOS | `~/Library/Application Support/harness-talk/mail.sqlite3` |
| Windows | `%LOCALAPPDATA%\harness-talk\mail.sqlite3` |

On Windows `~` is the directory in `USERPROFILE`, and a workspace is saved as `C:\dir` and compared without regard to case or to which slash separates its parts.

## One change on every system

A writer waits up to five seconds for another that holds the mailbox. That budget was a count of short pauses; it is now time by the clock. On Linux the wait ends at five seconds as before. On macOS, where a pause lasts longer than asked, the same wait took about 19 seconds on the runner and takes 5 now.

## Limits on the new systems

- Windows: `watch` does not notice that its reader has gone until its next line.
- Windows: the MCP server ends a cancelled tool call at once, without the grace period Unix gives. A process that an `mcp --connect` connector starts in its first moment can outlive it.
- Windows: the default mailbox is as private as the profile directory; htalk sets no access list.
- macOS: `PRAGMA fullfsync` is off, so a message saved a moment before a power loss can be missing afterwards.
- Both: OpenCode was checked against the test server of the suite, not against a real OpenCode. The session receivers of `integrations/` were not run.

## Code, tests and dependencies

- Production code: `src/` is 10,848 lines; in 0.13.0 it was 10,259. `src/os/` holds everything that differs between systems. The core that every command runs through is 43.3k tokens by `scripts/core_tokens.py`, and 76.5k with the adapters; in 0.13.0 it was 41.5k and 74.7k.
- Tests: 261, of them 195 in Python that run the installed command, 58 in Rust and 8 in Node. On Linux 55 of the Rust tests run, on macOS 18, on Windows 16. Of the Python tests 87 are the contract that runs on macOS and Windows; macOS skips 29 tests and subtests and Windows 31, each with its reason.
- Dependencies: the lock file lists 205 packages, as in 0.13.0. `windows-sys`, already in it, is a direct dependency on Windows only.
- Rust 1.88 is still the lowest supported version.
- Wheels: Linux x86-64 and ARM64 as before, and macOS ARM64, macOS x86-64 and Windows x64. Each new wheel was installed and run on a runner of its own system and architecture. The Windows executable carries its C runtime and asks for no Visual C++ redistributable. That is checked by the names it imports: no machine without the redistributable has run it.

## Source validation and limits

`tests.yml` runs on Linux, macOS and Windows on every pull request. On Linux every check of 0.13.0 passes, and `tests/agent_view/` differs from 0.13.0 by seven lines: the new code twice in `errors.txt`, and in `texts.txt` five source texts that no answer on Linux shows: the help of `--db` on the two new systems, the help and the advice of a command that is not ported, and the form of an `htalk mcp` failure.

These checks do not show a notice arriving in a live client. The native check of this release runs on the published artifacts on Linux, by the procedure of [releasing](../releasing.md), and is recorded when it is done.
