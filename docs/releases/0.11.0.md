# htalk 0.11.0

This release fixes mailbox recovery, catalogue selection, native transport I/O and receiver lifecycle behavior. It keeps mailbox schema 3. The receiver upgrade requirements below are intentional compatibility changes.

## Changes

- A ready saved answer returns without waiting for another SQLite writer. Wait-return receipts and registration removal remain best effort. Explicit empty message IDs are rejected; omitted send IDs still generate a new ID.
- Legacy schema validation rejects missing required tables or columns before creating another backup. Later migration failures can still leave a completed backup. Existing backups are preserved.
- Catalogue continuations preserve pagination and body selection. Canonical UUID selectors refer only to profile identity, including absent or retired profiles. A UUID-shaped display name must be selected through its own profile ID. Duplicate native identities use canonical UUIDs, and open clients recheck retirement and channel binding.
- OpenCode requires complete response framing, checks cancellation before POST, preserves uncertain outcomes without replay, and rejects bad saved-address rows individually. The first 50 SQLite-selected rows define the limit; a 51st row is only a limit sentinel. Invalid timestamps become null.
- Codex RPC uses shared I/O deadlines, preserves opaque socket queue receipts, and exposes terminal checked close for temporary stdio transports. Owned Rust subprocess groups retain their anchor through cleanup. Process disappearance during inspection is handled without relaxing anchor checks.
- Agent Zero suppresses stale wakes and stops after uncertain logging. Cline handles startup/detach ordering, Pi waits for watcher closure, and Copilot preserves pending work while its waiter owns the lock. Hermes owns its stdin and permits an explicit mailbox command set. Direct tools recommend stable send IDs but do not require them or retry automatically.
- Antigravity and Letta persist an active runtime phase until successful close and disposal. OpenHands records admission before native execution and keeps uncertain work blocked until explicit recovery. A consumed notice is separate from acknowledgment and external task completion.

## Upgrade

Stop receivers and other commands using the mailbox. Use SQLite's backup API to preserve the current database, and copy receiver state directories, catalogue configuration and trust files while their writers are stopped. Keep these backups private.

Update every htalk installation sharing the mailbox, and obtain matching adapter files from the 0.11.0 source archive:

```sh
uv tool install --force --no-build harness-talk==0.11.0
htalk --version
```

On schema 3, no migration command is required. For schema 1/2, the first ordinary command validates the legacy shape, writes and checks `PATH.backups/schema-OLD-before-3-UUID.sqlite3`, then migrates in one transaction. A failed migration preserves the original schema and any completed backup. Versions 0.5.1 and earlier cannot use schema 3. Never mix incompatible clients or manually change the schema version. See [database and recovery](../reference.md#database-and-peers).

Old Antigravity/Letta `idle` state lacks the new clean-shutdown evidence and cannot transparently resume. Inspect its status, native process state and history, then use the documented exact `--discard-session` recovery only if consciously retiring that native context is appropriate. Recovery saves the original state in a retirement receipt and preserves profile files; future work starts a fresh native session. Updating the package does not discard context automatically. Passive status and explicit recovery remain available when the interpreter lacks pidfd APIs. See [Antigravity](../../integrations/antigravity.md) and [Letta](../../integrations/letta.md).

OpenHands now requires `HTALK_OPENHANDS_STATE`, a private admission directory for one conversation/mailbox binding. Earlier launches had no admission ledger, so inspect saved mail and native history before the first upgraded launch. Do not create a new directory to bypass uncertain work. Use the [passive status and recovery commands](../../integrations/openhands.md) for an existing ledger.

Rust subprocess cleanup needs Linux 5.3+ and readable `/proc` metadata. Managed Python receivers additionally need usable `os.pidfd_open` and `signal.pidfd_send_signal`; Python 3.11+ by itself is insufficient. Unsupported builds refuse before changing receiver state or starting native work. This requirement applies to the affected process/managed routes, not a new Python runtime dependency for the standalone Rust mailbox executable. Cleanup covers observed processes that remain in the owned group with the expected ownership; escaped descendants and inaccessible metadata remain outside its success guarantee.

After updating, verify `htalk --version`, `htalk peer list`, the selected receiver's passive status and a read-only catalogue connection. Preserve profile IDs, host keys, trust files, session binding and saved queue receipts. Check stored mail before any explicit retry of uncertain delivery.

## Rollback and proof limits

The CLI retains schema 3, but reverting the executable does not reverse native actions or make newer receiver state safe for an older adapter. Stop all affected processes before considering rollback to a matched older CLI/source version. Preserve the current mailbox and receiver state, inspect native history and reconcile uncertain requests first. Do not delete ledgers or restore an old mailbox over later messages. htalk never restores backups automatically.

Source validation before release preparation passed 92 Rust tests, 146 Python tests on each of Python 3.11 and 3.14, 12 JavaScript watcher tests, Clippy and formatting. These tests use synthetic mailboxes and owned fixture processes. They do not establish native crash durability, orphan-runtime behavior, exactly-once external work or automatic failover. Publication workflow and exact-wheel native results belong to the [GitHub release](https://github.com/jointsome0-lgtm/harness-talk/releases/tag/v0.11.0), and dated native check documentation follows separately. Earlier native reports remain observations of their recorded versions.
