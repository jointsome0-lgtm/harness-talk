# htalk 0.11.1

This patch fixes migration replay after a write transaction has begun. A send or reply opening a schema-1/2 mailbox could encounter an external reader after migration BEGIN, roll back, enter admission and run migration again, creating another retained backup. It now uses normal SQLite waiting after successful migration BEGIN. Existing completed backups are retained.

Mailbox schema remains 3. Existing schema-3 mailboxes need no migration. The first ordinary command opening schema 1/2 still validates the legacy database, creates and verifies a private SQLite backup in `PATH.backups`, then upgrades it to schema 3 in one transaction. A failed migration preserves the previous schema and any completed backup. Message IDs, replies, acknowledgments and notification receipts keep their existing contracts.

## Upgrade and rollback

Stop active mailbox writers and receivers before upgrading. Preserve a consistent mailbox backup using SQLite's backup API, and copy receiver state, catalogue configuration and trust files while their writers are stopped. Keep the database, backups and state private.

After 0.11.1 artifacts are published, update every htalk installation sharing the mailbox and obtain matching adapter files from the 0.11.1 source archive. For an existing uv-installed CLI using a published Linux wheel:

```sh
uv tool install --force --no-build harness-talk==0.11.1
htalk --version
htalk peer list
```

Without uv, run `python -m pip install --upgrade harness-talk==0.11.1` in the intended Python environment. Keep the same mailbox paths, profile IDs, native session bindings and saved receipts. Verify the selected receiver's passive status before resuming work. Inspect stored mail before any explicit retry of uncertain delivery. Never delete or reset state to bypass recovery.

The [0.11.0 adapter, recovery and host requirements](0.11.0.md#upgrade) still apply, including Antigravity/Letta retirement of old idle state, OpenHands private admission state, and Linux `/proc`/pidfd requirements for affected process and managed routes. See [database and recovery](../reference.md#database-and-peers) for schema compatibility.

Rollback to a matched 0.11.0 CLI and adapter set keeps schema 3 compatible, but restores this migration replay bug for legacy mailboxes. Stop affected processes and preserve their current state before rollback. Reverting the executable does not reverse native actions or reconcile uncertain work. Never restore an old mailbox over later messages; htalk does not restore backups automatically.

## Validation and limits

Validation of the patch source passed 53 CLI compatibility tests and 95 Rust tests, plus Clippy and formatting. Synthetic schema-1/2 fixtures cover send and reply with an external reader blocking migration completion: the published 0.11.0 control entered admission and replayed migration; the fixed source waits without admission, preserves one verified backup, then saves successfully after reader release. Idempotent retry and notification boundaries remain covered.

Published 0.11.1 artifacts and checks against those exact artifacts are pending. This patch adds no native-client or performance validation claim. The fresh 0.11.0 baseline's seven performance failures remain unresolved; no new performance run was performed for this patch. Synthetic tests do not establish power-loss durability, starvation freedom or native delivery. Earlier native checks remain evidence only for their recorded versions.
