# htalk 0.11.1

This patch fixes migration replay after a write transaction has begun. A send or reply opening a schema-1/2 mailbox could encounter an external reader after migration BEGIN, roll back, enter admission and run migration again, creating another retained backup. It now uses normal SQLite waiting after successful migration BEGIN. Existing completed backups are retained.

Mailbox schema remains 3. Existing schema-3 mailboxes need no migration. The first ordinary command opening schema 1/2 still validates the legacy database, creates and verifies a private SQLite backup in `PATH.backups`, then upgrades it to schema 3 in one transaction. A failed migration preserves the previous schema and any completed backup. Message IDs, replies, acknowledgments and notification receipts keep their existing contracts.

## Upgrade and rollback

Stop active mailbox writers and receivers before upgrading. Preserve a consistent mailbox backup using SQLite's backup API, and copy receiver state, catalogue configuration and trust files while their writers are stopped. Keep the database, backups and state private.

Update every htalk installation sharing the mailbox and obtain matching adapter files from the 0.11.1 source archive. For an existing uv-installed CLI using a published Linux wheel:

```sh
uv tool install --force --no-build harness-talk==0.11.1
htalk --version
htalk peer list
```

Without uv, run `python -m pip install --upgrade harness-talk==0.11.1` in the intended Python environment. Keep the same mailbox paths, profile IDs, native session bindings and saved receipts. Verify the selected receiver's passive status before resuming work. Inspect stored mail before any explicit retry of uncertain delivery. Never delete or reset state to bypass recovery.

The [0.11.0 adapter, recovery and host requirements](0.11.0.md#upgrade) still apply, including Antigravity/Letta retirement of old idle state, OpenHands private admission state, and Linux `/proc`/pidfd requirements for affected process and managed routes. See [database and recovery](../reference.md#database-and-peers) for schema compatibility.

Rollback to a matched 0.11.0 CLI and adapter set keeps schema 3 compatible, but restores this migration replay bug for legacy mailboxes. Stop affected processes and preserve their current state before rollback. Reverting the executable does not reverse native actions or reconcile uncertain work. Never restore an old mailbox over later messages; htalk does not restore backups automatically.

## Validation and limits

Patch source validation passed 53 CLI compatibility tests and 95 Rust tests, plus Clippy and formatting. Synthetic schema-1/2 send and reply fixtures reproduce migration replay with the published 0.11.0 control and verify that 0.11.1 waits after successful migration BEGIN, preserves one verified backup and saves after the reader releases its lock.

The [0.11.1 publish workflow](https://github.com/jointsome0-lgtm/harness-talk/actions/runs/37141672055) built source commit `3c86ebb62151fe77ef5019082269f3ea2020665f`. Captured build-job logs for both Linux architectures passed 95 Rust tests, 95 installed Python tests, 8 hook tests, tool/recovery suites of 5 and 25 tests, 16 managed tests and 12 JavaScript tests, with no unexpected skips. These are recorded suite counts; they must not be added together as a count of unique tests. The x86-64 job also reports a successful source-distribution install.

The completed publish run uploaded three files to [PyPI 0.11.1](https://pypi.org/project/harness-talk/0.11.1/): both Linux wheels and the source archive. All three downloaded PyPI files matched the checked workflow bytes, SHA-256 hashes and sizes. A fresh x86-64 virtual environment installed the downloaded wheel and passed package-version, `htalk --version`, `htalk --help` and `pip check` checks. The lightweight tag `v0.11.1` points to the exact source commit. The [GitHub release](https://github.com/jointsome0-lgtm/harness-talk/releases/tag/v0.11.1) was read back with the expected body and three uploaded assets whose API hashes and sizes match; GitHub asset bytes were not separately downloaded. ARM64 had CI installed-wheel coverage and public-file byte comparison, without a separate local ARM64 execution check.

A fresh check against this run's exact x86-64 wheel and source archive passed the mandatory native exchange for 14 available installed clients. Codex with GPT-6.1 Sol high and Claude Code with Opus 5.5 high used actual model calls. Twelve other native clients used deterministic loopback providers and synthetic mail, with no paid inference. Each successful case observed a native notice, showed the full request once, validated its metadata, ACKed separately, sent a correlated reply, read and ACKed that reply at the controller, and ended with empty inboxes. Owned process closure was checked separately. See the [scoped native check](../checks/2026-10-03-0.11.1-native.md) for versions and limitations.

The strict combined runner aggregate remains false. Hermes retained an extra rejected local provider request; Hermes and Gemini did not establish normal native exit. Their mandatory mail exchanges and owned closure passed. OpenCode's headless server was stopped after its successful exchange. Notification cleanup remains a separate receipt: absent, unsupported and skipped do not prove removal. Antigravity SDK and Agent Zero were not checked because required installed prerequisites were absent.

The 0.11.0 baseline's seven performance failures remain unresolved, and no new performance run was performed for this patch. Synthetic tests do not establish power-loss durability or starvation freedom. Canned-provider checks do not establish model comprehension or external inference, and scoped process closure does not establish a host-wide absence guarantee. Earlier native checks remain evidence only for their recorded versions.
