# htalk 0.14.0 Windows desktop check, October 10, 2026

Recorded from the [report on #118](https://github.com/jointsome0-lgtm/harness-talk/issues/118#issuecomment-6101619568). The commands and output below are the sanitized observations of the published 0.14.0 wheel, not a check of the later source. The repository owner subsequently asked for this record and the supported Windows cells in [the platform page](../platforms.md) to be merged and #118 closed.

The owner selected this existing computer. The functional observations matched the expected results after the environment retry described below: exact Windows wheel/hash, version and help, clean pip check, default mailbox and inherited ACLs, successful exchange, unsupported commands, console interruption and Cyrillic. No htalk defect was observed in the executed functional steps. This is an agent-driven interactive console check, with the protocol differences recorded explicitly.

## Machine and input method

- Existing installation in use, not a new VM or Windows Sandbox.
- Windows 10 Pro (EditionID Professional), 22H2, build 19045.6456, x64 / AMD64.
- Existing Python 3.12.2 x64, selected with the py launcher. Windows installation records list Python 3.12.2 (64-bit), its Core Interpreter and Executables, with publisher Python Software Foundation. This establishes PSF Windows-installer provenance; the original download channel (python.org versus winget) was not independently established. No Python installer was run for this check. The python command resolves to a different WindowsApps interpreter, so py was used consistently for the existing 3.12.2 installer distribution.
- vcruntime140.dll was already present in System32. This record does not demonstrate a desktop without that runtime. No Visual Studio, build tools or redistributable was installed.
- Interactive cmd.exe was run through Codex exec_command with tty=true on Windows ConPTY. Commands were entered separately at the prompt; no batch file ran the check. Windows PowerShell 5.1.19041.6456 was started by typing powershell in that same console and exited back into cmd.exe. The host launching the terminal was PowerShell 7.
- Ctrl-C was sent once as U+0003 through terminal input, after approximately 3.2 seconds for each send, and after ready plus the message event for watch. No Ctrl-Break, direct process signal, process termination or physical human keyboard press was used. The input route is a pseudoconsole, not a separately observed native console window or SSH session.
- cmd.exe reported code page 866. PowerShell reported OutputEncoding utf-8 before any encoding change.
- No client was installed or signed in. Sent fixture text was limited to the texts in this issue.

## Differences and limits, one per line

- The first pip install and download returned No matching distribution found, exit 1, while the inherited environment had PIP_NO_INDEX=1. Those results are retained below.
- PIP_NO_INDEX was then cleared only in a new test-console environment; install and download succeeded. This environmental retry is a departure from the issue's literal no-workaround instruction, not a code fix. The functional observations below are from the retry.
- The initial setup used a restricted terminal session; a new approved terminal session was used for PyPI access and writing the specified default mailbox. The mailbox-absence guard was repeated in the new session before any htalk command. All functional mailbox, unsupported-command, Ctrl-C and Unicode steps used that one new cmd.exe session, with nested PowerShell.
- py was substituted for python to use the existing PSF installer distribution. Its exact original download channel remains unknown.
- Input was agent-driven through ConPTY. A physical human key press and an independently visible console window were not checked. A physical-keyboard or separately observed native-console check is outside this record.
- PowerShell printed Cannot load PSReadline module. Console is running without PSReadline. It was left as observed.
- A supplementary pip-configuration inspection initially used the wrong constructor signature and printed TypeError; its corrected form returned an empty configuration-key list. No index URL, extra index or find-links configuration was present after clearing PIP_NO_INDEX; pip used its default PyPI index. Both supplementary commands are included below.
- Cleanup used native PowerShell Remove-Item instead of cmd.exe rmdir/del. Targets were resolved and checked, and only the four paths created by this check were removed.
- The linked issue comment is the primary verification artifact. This record and the supported Windows cells of docs/platforms.md preserve that evidence. No htalk code was changed. This is not evidence of a real client or the platform table's Live status.
