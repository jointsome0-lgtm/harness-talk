# htalk 0.14.0 native check, October 8, 2026

Three installed clients completed the native exchange on Linux against the exact x86-64 wheel and source archive from [publish run 37816480059](https://github.com/jointsome0-lgtm/harness-talk/actions/runs/37816480059), source commit `09bddc31339faa1a7585da64f87968665f14fa8a`: Codex and Claude Code as real sessions in both initiating directions, and OpenCode as a real server with a deterministic local provider. This is the scope the repository owner set for 0.13.0, kept for 0.14.0. The other eleven installed clients were not checked live for this release; their last live check is the [0.12.0 native check](2026-10-05-0.12.0-native.md).

No client ran on macOS or Windows. 0.14.0 is the first release with wheels for those systems, and what stands behind them is the publish run on GitHub's hosted runners, described below. A runner is not a person's machine with real clients; [what works on which system](../platforms.md) says which of the two backs each part.

What each executable asks of its system was read from the wheels. The Windows one imports libraries of Windows only: `VCRUNTIME140.dll` and the `api-ms-win-crt` libraries are not among them, so it needs no Visual C++ redistributable. The macOS ones link `libSystem` and `libiconv`, which the system has, and say macOS 11.0 on ARM64 and 10.12 on x86-64, as their wheel tags do. The ARM64 one carries a code signature.

The Windows executable was also started where that runtime is absent. On a Windows runner, [run 37820215792](https://github.com/jointsome0-lgtm/harness-talk/actions/runs/37820215792) took the Windows wheel of this publish run, with the hash above, and ran its executable in the `nanoserver` and `servercore` images of Windows Server 2025, build 26100. Neither image has `vcruntime140.dll` in `System32`; the runner itself has. In both images the executable printed `0.14.0`, registered two pull peers, saved a message and listed it, with exit status 0 wherever the check printed one, and the mailbox was `mail.sqlite3` under `%LOCALAPPDATA%\harness-talk`. The executable of the cancelled run, started beside it, ended with -1073741515 in both, the status of a library that was not found. A container is not a desktop.

In the run each Linux architecture passed 131 tests of the installed wheel outside the checkout, 8 of the agent view, and the adapter suites. Each macOS wheel was installed outside the checkout on a runner of its own architecture and ran the 87 contract tests of that system. It skipped 29 tests and subtests, all of native delivery to Codex and Claude Code, which is not ported there. The Windows wheel ran the same 87 and skipped 31: those 29, and two that watch a send through a named pipe in the file tree, which Windows does not have.

Each client ran as an ordinary interactive session in its own empty workspace, with the account's normal client configuration, in a terminal multiplexer started with a clean environment. The mailbox was new and the text invented. These were actual model calls. Token counts and billing were not measured, and the model names are the ones the clients displayed. Codex offered an update to 0.161.0 at start; it was declined.

Each recipient compared the shown id with the id in its notice and checked sender, recipient, body and `in_reply_to` before the ack. All four rows are acknowledged and both final inboxes are empty. Each session's own transcript holds exactly its two notices. No result in either transcript carries `recovery`, `next_action` or `notification_started_at`, which an executable older than 0.13.0 would print. Both sessions printed `0.14.0` for `--version` before the exchange, and every htalk command in both transcripts names the wheel's executable by its absolute path. The mailbox is on schema 3. The exchange ran from 17:40:42 to 17:43:40 UTC.

Ack cleanup was literally `unsupported` with `client_has_no_notification_removal` for Claude and `absent` with the queue id for Codex. Neither proves that a notice was removed. Both clients ended with exit status 0 after their own quit command.

## OpenCode

OpenCode 1.18.32 ran as `opencode serve` on a loopback port with new state directories and a fake key. The model was a local script that speaks the chat-completions protocol on loopback, so no model call was made and the result says nothing about model comprehension. Only the htalk MCP tool, bound to the wheel's executable, was offered to it.

`peer check` reported the session as `idle` on a server of version 1.18.32. A pull peer acting as controller sent one question. htalk answered `submitted` with `opencode_prompt_async_accepted` and returned the answer inside its 45-second wait. The session's own history holds the notice once and three tool calls: show, ack, reply. The local provider checked id, sender, recipient, body and `in_reply_to` of the shown message before it asked for the ack. The controller showed the answer, checked that it answers the question, and acknowledged it separately. Both final inboxes are empty. The provider served five requests, one for the session title and four for the exchange.

Ack cleanup was literally `unsupported` with `client_has_no_notification_removal` in the session and `skipped` with `pull_only` at the controller; neither proves that a notice was removed. The server ended with -15 after SIGTERM, which is not a normal exit of its own. A request for port 0 selected 4096, so an OS-assigned port was not shown. No attached TUI was checked.

## Scope and limits

- Linux x86-64 only. No Codex, Claude Code or OpenCode ran on macOS or Windows, and no wheel but the Linux x86-64 one was executed outside the publish run.
- On Windows the executable ran on the runners and in two Windows Server containers, and on no desktop. Installation from PyPI there, a person's profile and Ctrl-C from a keyboard were not observed. [#118](https://github.com/jointsome0-lgtm/harness-talk/issues/118) is that check; it was not done when this was written.
- Not checked live for 0.14.0: Pi, Oh My Pi, OpenClaw, Cline, Kilo, Goose, Hermes, GitHub Copilot CLI, Gemini CLI, Letta Code and OpenHands. Here their adapters are covered only by the adapter tests of the publish run. Antigravity SDK and Agent Zero remain unchecked, as before.
- The notice names `htalk`. Both core sessions ran the wheel's absolute path in its place, as in the [0.13.0 check](2026-10-07-0.13.0-native.md), where an older htalk on the same machine came first in the environment Codex gives its commands. A notice followed word for word on a machine whose first `htalk` is 0.14.0 was not observed.
- One exchange in each direction. No interruption, recovery, concurrent writer or route between devices was exercised. The wait for a busy mailbox, which this release times by the clock, was not exercised live; the tests of the publish run cover it.
- Native exit was observed as an exit status. What htalk owns while it delivers, process groups, pidfds and listeners, was not observed closing in this check; the tests of the publish run cover it on Linux.
- The clients used the account's normal configuration and network. Nothing is claimed about the processes or the traffic of the whole host.
- The installed clients and the older installed htalk were not changed.
