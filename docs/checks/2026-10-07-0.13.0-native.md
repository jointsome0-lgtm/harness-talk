## OpenCode

OpenCode 1.18.32 ran as `opencode serve` on a loopback port with new state directories and a fake key. The model was a local script that speaks the chat-completions protocol on loopback, so no model call was made and the result says nothing about model comprehension. Only the htalk MCP tool, bound to the wheel's executable, was offered to it.

A pull peer acting as controller sent one question. htalk answered `submitted` with `opencode_prompt_async_accepted` and returned the answer inside its 45-second wait. The session's own history holds the notice once and three tool calls: show, ack, reply. The local provider checked id, sender, recipient, body and `in_reply_to` of the shown message before it asked for the ack. The controller showed the answer, checked that it answers the question, and acknowledged it separately. Both final inboxes are empty. The provider served five requests, one for the session title and four for the exchange.

Ack cleanup was literally `unsupported` with `client_has_no_notification_removal` in the session and `skipped` with `pull_only` at the controller; neither proves that a notice was removed. The server ended with -15 after SIGTERM, which is not a normal exit of its own. A request for port 0 selected 4096, so an OS-assigned port was not shown. No attached TUI was checked.

## Attempts that are not counted

Both stay recorded because they happened; neither left uncertain work in the mailbox that was accepted.

- OpenCode, first attempt. The provider script read the tool result wrongly and stopped after show. htalk had submitted the notice and answered show correctly. The request stayed unacknowledged in that attempt's mailbox, which was not used again. The script was corrected and the check ran from new state.
- Codex and Claude, first attempt. It completed in both directions with four acknowledged rows, but the commands of the Codex session were run by an htalk 0.11.1 installed on the same machine: the shell environment Codex gives its commands puts that directory first. The results in its transcript carry the three times, which a 0.13.0 result does not. That attempt is therefore an exchange between 0.11.1 and 0.13.0 on one mailbox, and not a check of 0.13.0 on both sides. The accepted attempt used new sessions and a new mailbox, and both sessions were told to run the wheel's executable by its absolute path.

## Scope and limits

- Not checked live for 0.13.0: Pi, Oh My Pi, OpenClaw, Cline, Kilo, Goose, Hermes, GitHub Copilot CLI, Gemini CLI, Letta Code and OpenHands. Here their adapters are covered only by the adapter tests of the publish run. Antigravity SDK and Agent Zero remain unchecked, as before.
- The notice names `htalk`. Both core sessions ran the wheel's absolute path in its place, for the reason given above. A notice followed word for word on a machine whose first `htalk` is 0.13.0 was not observed.
- One exchange in each direction. No interruption, recovery, concurrent writer or route between devices was exercised.
- The clients used the account's normal configuration and network. Nothing is claimed about the processes or the traffic of the whole host.
- The installed clients and the older installed htalk were not changed.
